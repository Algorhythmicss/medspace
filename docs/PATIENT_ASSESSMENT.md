# Patient initial assessment

Implementation record: **2 November 2026**. This feature belongs to the original clinic app, not `/demo`. Local implementation, verification, GitHub publication and hosted availability are separate states. Nothing here establishes clinical effectiveness or a complete security certification.

## Contract and scope

A patient with a current signed care link or patient session can answer three fixed, versioned questions: their concern, when it started/what changed, and relevant medicines/allergies/past conditions. Each answer is required and limited to 2,000 characters; “none” and “not sure” are valid responses. English and Hindi prompts are provided. Wording is an initial product choice, not a clinically validated questionnaire or triage instrument.

The patient can attach up to three files: 2 MiB per file, 3 MiB combined. Accepted extensions are JPEG, PNG, WebP, single-frame GIF, AVIF, single-page TIFF, PDF, DOCX, XLSX, PPTX, ODT, ODS, ODP, RTF and UTF-8 TXT. “All formats” is deliberately not interpreted as unrestricted execution-capable uploads. Executables, scripts, HTML, SVG, general archives, macro-enabled Office extensions, animated images, multi-page images and unsupported/corrupt data are rejected. HEIC and legacy binary Office files are not supported in this first version; export them to an accepted format. Office format identification probes bounded ZIP metadata, but nothing is unpacked onto disk. No OCR, execution of uploaded code, model deserialization or AI interpretation is performed.

Answers remain patient-reported. An authenticated doctor can mark an assessment reviewed or dismiss it, but that never promotes medicine/allergy/condition text to verified chart facts. The form does not book a visit, confirm that a doctor has read it or provide urgent triage. Existing history-submission and clinic workflows remain separate.

## Trust boundaries and invariants

Browser → same-origin POST → signed patient credential → current database link version → persistent request budget → bounded multipart parser → strict questions/consent/file limits → isolated format detection/image rewriting → private malware verdict/quarantine → atomic ownership/quota/idempotency checks → clinician review → authorized attachment download.

- Ownership is derived from a signed credential, never a submitted patient ID. An explicit invalid bearer credential cannot fall back to a different cookie identity. Link version is checked again under a row lock when saving, and on every patient download.
- The exact API path bypasses the page proxy only because the handler independently authenticates it. Doctor and staff cookies cannot authorize patient submissions. Staff cannot review assessments, rescan attachments or fetch files.
- Writes require an exact same-origin Origin and reject cross-site fetch metadata. Compressed requests are rejected. Actual streamed bytes, not just Content-Length, are capped at 3 MiB + 64 KiB, with an eight-second body-read deadline. Unknown fields, duplicate answers and duplicate consent are rejected.
- Signature detection and image decoding run in a disposable worker with a five-second deadline and bounded JavaScript heap. This is a worker thread, not an operating-system security sandbox; native/external allocations are not covered by the heap limit. Images are limited to 16 million pixels, one frame/page, and 2 MiB after rewriting. Rewritten lossless WebP files discard metadata and appended original bytes; no original photo is retained. This is not a claim that native decoders are invulnerable.
- Documents are never rendered or executed on the app origin. They require a clean private ClamAV verdict before download; unavailable/error/timeout verdicts stay quarantined. A positive detection rejects the entire incoming submission. Retried scans that detect malware leave the stored file blocked. A clean scan is not proof that a downloaded document is harmless; do not enable macros or active content.
- Attachment delivery always uses `application/octet-stream`, attachment disposition, a sanitized/encoded filename, no-store, nosniff, same-origin resource policy and a restrictive sandbox CSP. Binary bytes are never selected into patient/doctor page payloads.
- The database enforces deny-all RLS with no PUBLIC/anon/authenticated grants on all three new tables, answer-size/state checks, byte-count checks and patient-scoped unique submission keys. The application writes using its existing server-only database role.
- A patient has 12 authenticated submission attempts/hour, three accepted assessments/rolling 24 hours, three pending assessments and 24 MiB lifetime attachment storage. Patient-row serialization makes concurrent quota checks and writes atomic. A stable UUID plus a canonical payload hash makes identical retries idempotent and different payloads with an old key conflict rather than overwrite. No automatic clinical-record deletion is introduced.
- Patient merges retain every assessment and attachment, remap colliding patient-scoped submission keys, and combine active upload budgets conservatively. Sorted patient-row locks prevent an in-flight upload from being missed and cascade-deleted. If a merged record already exceeds the attachment allowance, new attachments are blocked but answers without attachments remain possible.
- An infected rescan takes precedence over concurrent or delayed clean receipts. Rejected files cannot be resurrected by a stale clean result.
- No answers, tokens, filenames, file contents or clinical database errors are logged or sent as analytics events. File scanning is not delegated to a public reputation service.

The updated patient-merge action needs the additive schema even when the intake UI is disabled. Apply the migration before deploying this source; the feature flag is not a substitute for that ordering. Private ClamAV configuration: `MEDSPACE_CLAMAV_HOST`, optional `MEDSPACE_CLAMAV_PORT` (default 3310), and `MEDSPACE_CLAMAV_TLS=true` for every non-loopback host. Remote connections use normal certificate/hostname verification; do not disable it. The scanner must be clinic-authorized and privately operated, kept current, resource-limited and configured to flag encrypted/unscannable and limit-exceeding content rather than treating it as clean. Public unencrypted clamd must never be exposed. Provisioning that service or transferring real patient data to a new provider needs an explicit infrastructure/privacy decision; this implementation does not purchase or configure a hosted scanner.

Without a configured/available scanner, patients can still submit answers and rewritten photos. Supported documents are received into private quarantine, clearly labeled, and remain impossible to download until an authenticated doctor retries a successful private scan. This is a deliberate fail-closed limitation, not a completed document-scanning deployment.

Release only the selected original-app changes, preserving the already deployed white background and privacy-filtered analytics. Do not include the dirty synthetic-demo implementation, change its project link or repoint the original app at a demo database. Schema-management verification does not prove the Vercel database credential works. Before enabling the feature, run `pnpm exec tsx scripts/check-assessment-schema.ts` in the deployment build environment. It uses the application's PostgreSQL driver, a read-only transaction, ten-second connection/query limits and a twenty-second overall deadline to inspect only schema/access metadata. It does not load a local environment file or print credentials, URLs or raw database errors. Keep the production feature flag disabled if this gate fails. Run the trace-only packaging suite after the Linux production build and before promotion. Do not deploy a source update ahead of required schema.

## Verification matrix and evidence status

Required checks: answer validation; format/MIME spoofing; hidden filename/control characters; executable/archive rejection; metadata/polyglot stripping; corrupt/animated/pixel-bomb input; streamed size cap; missing consent; CSRF; anonymous/wrong-role/expired/revoked credentials; cross-patient file reads; quarantined-file denial; exact clean versus infected/error scanner receipts; real local ClamAV clean/EICAR controls when available; concurrent idempotency and quotas; failed-write rollback; clinician review without chart promotion; browser persistence/reload/mobile usability; and production-build dependency tracing for workers.

The mutation oracle must reject a predicate that allows a quarantined attachment to download. `scripts/test-assessment-package.ts` reconstructs only the inspector route's traced dependencies into a temporary directory, runs image/document workers there, then removes the copied native decoder to prove the packaging oracle fails. The trace must include worker dependency links, JavaScript dependencies and platform-specific Sharp/libvips binaries, not just the top-level packages. All database/browser fixtures must be synthetic and limited to a database named `medspace_assessment_test` on loopback. The separate existing `test-patient-link.ts` is preserved unmodified. The dated verification record identifies actual test results and unavailable hosted checks; do not treat this design document as evidence those checks passed.

Rollback first disables the feature flag while retaining the additive schema and merge-aware application code. Once assessments exist, do not blindly return to an older artifact whose merge action does not preserve these new child records. Any code rollback must retain that preservation fix or disable patient merging until a compatible artifact is restored. Preserve uploaded records; no destructive down migration or clinical-data reset is part of rollback. An outage or absent scan verdict must not unlock documents.

## Residual risks and open decisions

The original app is a singleton clinic, not a multi-clinic tenant architecture. Existing pre-feature report/history upload endpoints are not certified by this feature's test suite; broader legacy-upload hardening remains separate. Link possession grants the patient authority until expiry/revocation, so leaked links remain sensitive even with budgets. File signatures and malware scanners are imperfect. Native image libraries require patching and monitoring. Hard storage caps can interrupt attachment intake, so the clinic needs a contact/fallback process. Retention, backups, approved scanner hosting, exact question wording and real clinician/patient acceptance remain unresolved; no automatic retention or commercial/clinical claims are introduced.
